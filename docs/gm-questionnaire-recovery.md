# GM questionnaire assignment and quarterly answer recovery

Questionnaire PATCH writes require an explicit module list and the `updatedAt` value returned by the server. The row is locked before comparing versions. Missing versions, stale versions and unconfirmed removal of all assigned modules fail without changing assignments. The editor preserves assigned IDs while its catalogue loads, blocks incomplete saves, and marks a deliberate removal of all selected modules. Successful writes log the before/after module IDs without question or answer contents.

GM Standard/Flex/Billa questions in server-resolved modules designated `Distributionsziel Qn/YYYY` reuse valid answers within that calendar quarter, independently of manual bonus calculations. Current Q4 modules use `Distributionsziel Q4/2026`. Other modules retain their existing RED-month behavior. Existing technical Durcharbeit quarterly eligibility remains in place. Photo questions are excluded from quarterly completed-answer copying.

The explicit `POST /markets/gm/visit-sessions/:sessionId/resume-quarter-answers` operation authenticates the owning GM and operates only on a nondeleted draft. The GM visit page invokes it when resuming a draft; the existing token/selection resume POST paths also invoke recovery. GET remains read-only. Recovery locks the session and its questions, then fills only eligible fields with no answer row or comment, including deleted rows. A saved blank, zero, invalid answer, hidden/skipped answer, comment or tombstone is preserved, as are touched sibling occurrences of the same question. Repeated recovery is idempotent.

Historical sources must belong to the same GM, market, technical question and quarter and pass the destination snapshot's answer validation. Recovery inserts new draft answer/option/matrix/comment rows using the existing copy routine. It never changes submitted source answers, copies photos into new completed answers, replaces existing draft fields or starts a replacement visit. Snapshot configurations are fetched only for actual recovery targets.

No schema migration, production configuration change or historical backfill is required. The production database was not used for development or tests.

Verification: 33 focused tests across the real authoring/visit routes, disposable synthetic PGlite data, existing quarterly reuse/validation tests and Spezialfragen regressions; backend TypeScript and optimized frontend builds; Chromium checks of both real editors with delayed/partial catalogues, a real stale-save API conflict, frontend GET/POST/GET recovery through the isolated backend and the error next to Starten at the GM tablet viewport. External auth, storage, bonus finalization and jobs are synthetic/stubbed in route fixtures. The legacy environment-based full `app.integration.test.ts` suite was not run; its two legitimate questionnaire save payloads were updated for the version contract.
